# 项目审查

## 总结

这是一个面向论文实验的灵巧手抓取执行评测项目，论文主题是“在物体位姿不确定性下进行协调接触控制”。

项目本身不是抓取姿态生成器，而是承接 BODex / DexLearn 的输出，完成：

1. 将不同来源的抓取数据转换成统一格式。
2. 对虚拟机械臂的基座姿态进行批量 IK。
3. 在 MuJoCo 中执行抓取、挤压、抬升和扰动测试。
4. 对比自己的控制方法与多个 baseline。
5. 统计抓取成功率、物体位姿误差、接触力和 wrench 指标。
6. 输出控制轨迹、评估结果和可视化数据。

整体属于“论文实验原型”，算法结构清楚，但工程稳定性、可复现性和异常处理还有较大提升空间。

## 一、项目实现流程

### 1. 入口与配置

入口是 `src/main.py`，使用 Hydra 读取：

- `config/base.yaml`
- `config/task/*.yaml`
- `config/hand/*.yaml`

然后通过动态函数名调用任务：

```python
eval(f"task_{cfg.task_name}")(cfg)
```

当前任务包括：

- `format`
- `dummy_arm_qpos`
- `control_eval`
- `control_stat`
- `eval`
- `stat`
- `vobj`
- `vusd`
- `collect`

### 2. 数据格式转换

`src/task/convert_format.py` 支持：

- BODex 数据格式
- DexLearn/Learning 数据格式
- Batched 数据格式

统一输出：

```text
obj_path
obj_pose
obj_scale
pregrasp_qpos
grasp_qpos
squeeze_qpos
```

BODex 数据还会针对不同机械手进行关节顺序调整、palm 平移修正、palm 旋转修正和坐标系转换。

### 3. 虚拟臂 IK

`src/task/dummy_arm_qpos.py` 使用 `pytorch_kinematics` 对抓取基座位姿求解虚拟臂关节：

```text
base pose + hand qpos
        ↓
dummy arm IK
        ↓
dummy arm qpos + hand qpos
```

支持批量处理、CUDA、IK 重试和参考姿态。

### 4. MuJoCo 仿真

核心仿真封装位于 `src/util/hand_util.py`。`MjHO` 负责：

- 加载手部 MJCF
- 加载物体 mesh
- 设置物体密度和摩擦
- 添加桌面
- 获取接触点、接触法向、接触力
- 控制关节
- 控制 mocap 或虚拟臂
- 渲染 viewer / video

每个样本都会重新建立物体和手部的 MuJoCo 模型。

### 5. 控制器

核心控制器是 `src/util/grasp_controller.py`。

主要步骤：

1. 根据接触位置和接触坐标系计算 grasp matrix。
2. 根据关节刚度和接触 Jacobian 计算接触刚度模型 `Ks`。
3. 使用两阶段控制：
   - Stage 1：沿抓取轨迹移动，同时限制接触切向运动。
   - Stage 2：根据接触力、摩擦锥、wrench balance 调整关节和接触力。
4. 使用 SLSQP 优化关节增量和接触力，同时加入关节限位、摩擦锥、接触力模型、目标握力和 wrench 约束。

目前支持：

- `ours`
- `op`
- `bs1`
- `bs2`
- `bs3`

baseline 的主要差异集中在是否使用机械臂运动、是否做接触力反馈、是否为各接触点分配相同目标力，以及是否使用多接触模型。

### 6. 统计

`src/task/control_stat.py` 读取控制记录，统计：

- 物体是否成功抬升
- 物体位置误差
- 物体旋转误差
- 总接触力
- wrench
- normalized wrench
- 失败样本和无效样本

最终输出 YAML 统计结果。

## 二、当前项目做得比较好的地方

### 算法组织较清晰

控制器、MuJoCo、机器人模型、IK、数据转换、统计模块基本分离，结构上便于继续扩展。

### 支持多种手型

已经支持 Shadow Hand、Allegro、Leap Hand / Tac3D、UR10e + Shadow，以及 dummy arm 组合。机器人定义通过 `RobotFactory` 注册，扩展方式比硬编码更好。

### 控制记录比较完整

保存了物体位姿、关节状态、接触信息、planned qpos、balance metric、优化耗时、stage 和优化结果，对后续分析和调试很有价值。

### 有 baseline 和 ablation 结构

`ours / op / bs1 / bs2 / bs3` 以及 `ablation_name` 允许比较不同控制策略，适合论文实验。

## 三、优先级最高的问题

### P0：异常被吞掉，实验可能“假成功”

`src/task/control_eval.py` 和 `src/task/evaluation.py` 都会捕获所有异常并只写 warning。批处理结束后仍然打印完成日志。这会造成：

- 某些样本实际执行失败，但任务仍显示完成。
- 最终统计只包含成功写出的文件。
- 用户无法知道失败样本数量和失败原因。
- 结果可能出现隐式样本选择偏差。

建议：worker 返回 `{path, success, error, traceback}`；主进程统一汇总失败清单；将失败结果保存成错误记录；如果失败率超过阈值，任务退出码非零。

### P0：SLSQP 优化状态没有检查

`GraspController.check_wrench_balance`、`ctrl_opt` 和 `ctrl_opt_bs3` 都直接使用 `res.x`，但没有检查 `res.success`、`res.status`、`res.message`、约束残差和关节限位。如果 SLSQP 不收敛，当前代码仍然会把不可行解发送给 MuJoCo。

建议：将 solver 状态加入 `r_data`；检查关节限位、摩擦锥和接触模型残差；优化失败时保持上一时刻 qpos、退化为位置控制或将样本标记为 invalid；保存优化失败原因。

### P0：统计函数对空数据不安全

`src/task/control_stat.py` 中成功率分母可能为零，空数组还会产生 NaN。应明确区分无输入、solver 失败、严重穿透、仿真失败、正常失败和 invalid，并输出 `num_total / num_valid / num_success / num_failure / num_invalid`。

### P0：`Batched` 数据输出路径存在嵌套错误

`src/task/convert_format.py` 的 `Batched` 函数在循环中不断覆盖 `save_path`，第二次循环开始可能生成：

```text
.../0.npy
.../0/1.npy
.../0/1/2.npy
```

应保留固定的 `base_save_path`，每次从原始路径生成目标文件名。

### P0：Leap 快速脚本的实验目录不一致

`script/test_learning_dummy_arm_leap_tac3d.sh` 中 format 和 dummy arm IK 使用 `exp_name=learn_2`，而 control eval 和 control stat 使用 `exp_name=learn`。如果从头执行脚本，后两个步骤可能找不到前面生成的数据。应统一 `exp_name` 或显式传递输入输出目录。

### P1：wrench balance 的摩擦锥梯度在零点不正确

当前梯度使用 `mu * np.sign(fx)`。约束是 `mu * fx - norm(fy, fz) >= 0`，在 `fx >= 0` 的边界下，法向导数应为 `mu`。当初始点 `fx=0` 时当前梯度为 0，可能降低 SLSQP 的收敛稳定性。建议增加有限差分梯度测试，并修正解析梯度；修复前应保存 golden results。

### P1：控制器存在潜在的未初始化变量

在 ours 和 bs2 的控制循环中，如果第一步就进入 Stage 2，会读取尚未赋值的 `desired_sum_force`。默认轨迹大概率会先经过 Stage 1，但仍应显式初始化。

## 四、可复现性问题

### 1. 依赖没有正式声明

`pyproject.toml` 目前只有 Black/Ruff 配置，没有项目元数据、依赖列表、Python 版本约束、安装入口、测试依赖和锁定版本。README 通过手工安装额外仓库，代码还调用特定 `pytorch_kinematics` API，例如 `build_chain_from_mjcf`。应固定 fork/commit，并提供 `environment.yml` 或 lock 文件。

建议增加依赖检查、Python 版本检查和独立的环境 preflight 脚本。

### 2. 示例数据依赖外部资产

仓库中的示例 `.npy` 引用了 `assets/object/DGN_2k/...`，但当前仓库没有 `assets/object`，README 要求额外下载 BODex 数据。应提供资产版本、下载地址、校验和、目录检查，并在缺失时给出可读错误。

### 3. 路径大量依赖当前工作目录

机器人定义使用 `assets/hand/...` 相对路径，配置中还包含机器相关绝对路径 `/mnt/disk1/...`。建议统一使用 `PROJECT_ROOT`、`ASSET_ROOT`、`DATA_ROOT` 和 `OUTPUT_ROOT`，启动时转换为绝对路径。

### 4. 随机种子不完整

`src/main.py` 只设置了 NumPy 和 Python `random`，IK 中使用的 PyTorch 随机数没有设置，多进程下也没有 worker 独立 seed。建议统一设置 NumPy、Python、Torch、CUDA seed，并保存 seed、git commit、完整 Hydra 配置、环境版本和输入数据列表。

## 五、工程结构和性能改进

### 1. 抽取重复控制循环

`tabletop_dummy_arm_ours.py`、`bs1.py`、`bs2.py`、`bs3.py` 有大量重复的状态读取、接触处理、轨迹插值、MuJoCo 执行和数据记录。可以把公共流程抽到基类或 runner 中，只保留每个 baseline 的策略差异。

### 2. 合并 `ctrl_opt` 与 `ctrl_opt_bs3`

两个优化器重复了大量变量定义、qpos 代价、关节约束、SLSQP 调用和结果解析。可以抽取统一优化问题构造器，由策略传入 force objective、force constraint、arm motion policy 和 equal-force policy。

### 3. 避免每个扰动重复初始化运动学模型

当前每个 offset 都会调用 `_initialize()`，同一个样本在多个扰动下会重复创建机器人、Pinocchio 模型和控制器。可以缓存 Robot、Pinocchio model 和 RobotAdaptor，每个 episode 只重置仿真和控制器临时状态，之后用 golden test 验证没有状态串扰。

### 4. 线性代数优化

`Ks` 中多处使用 `np.linalg.inv(A) @ B`。可以改为 `np.linalg.solve` 或缓存矩阵分解，减少每个控制周期的矩阵求逆。应以性能 profile 和数值误差测试为依据。

### 5. 控制并行度默认值过高

`config/base.yaml` 默认 `n_worker: 96`。每个 worker 都会创建 MuJoCo、Pinocchio 并执行 SLSQP，可能造成内存压力和 CPU oversubscription。建议根据 CPU 核数和内存自动设置较小默认值。

## 最终评价

项目科研目标明确，核心算法实现具备完整闭环：

```text
抓取姿态
  → 数据格式转换
  → dummy arm IK
  → MuJoCo 接触仿真
  → 两阶段接触控制
  → 抬升与扰动
  → 成功率 / wrench 统计
```

最大风险不是算法缺失，而是：

1. 失败样本被静默吞掉。
2. 优化器失败没有检查。
3. 输入、路径和依赖约定过于隐式。
4. 没有自动化测试。
5. 结果缺少可复现实验元数据。
6. baseline 和控制器存在大量重复代码。

如果目标是保持论文默认功能和结果不变，应优先处理异常可见性、数据校验、依赖锁定、测试和实验元数据，不要一开始修改控制目标、摩擦参数或 force threshold。审查过程中未修改项目源代码，工作区保持干净。
